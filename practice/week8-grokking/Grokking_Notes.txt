CODE (optional, only if it helps)
public static int binarySearch(int[] arr, int target){
    int start = 0;
    int end = arr.length -1;

    int foundIndex = -1;

    while(start<=end){
        int mid = (start+end)/2;
        if(arr[mid] == target){
            foundIndex = mid;
            break;
        }else if(target<arr[mid]){
            end = mid-1;
        }else{
            start = mid +1;
        }

    }
    return foundIndex;
}
WHY BINARY SEARCH IS O(log n):
Every step throws away half of the remaining list. So the question is:
"how many times can I cut n in half before only 1 item is left?"
That number is log n.

Example: 1,000,000 items
1,000,000 -> 500,000 -> 250,000 -> ... -> 1
That takes about 20 halvings, so at most about 20 steps.
Linear search could take up to 1,000,000 steps for the same list.

If the list doubles to 2,000,000, I only need ONE extra step,
because one more cut brings it back to the old size.
That is why log n grows so slowly.

IN MY OWN WORDS
Computer memory is like a wall of drawers outside a theatre. When I
store something, the computer gives me a drawer (allocates) and takes it
back when I'm done (frees).

Array: all items sit in drawers right next to each other. 10 items
need 10 free drawers in a row.
Linked list: each item carries a pointer to the next item's address, so
the items can sit in any free drawers, even far apart.

Because an array is one block, the computer can calculate where any
item is (start address + index) and jump straight there. A linked list
has no such shortcut. To reach the 7th node I must walk through
nodes 1 to 6 first.

In practice arrays are used more. Jumping to any index is fast, they
need less space (a list stores a pointer with every item), and neighbouring
items load into the cache together, so scanning is faster in real life.
Linked lists are still good when items are inserted or deleted a lot.

EXAMPLE
Drawers outside a theatre (memory).
Facebook-style usernames: an array of 26 slots (A to Z), where each slot
holds a linked list of names starting with that letter. The array jumps
to the right slot, and the list handles growth in that slot.

CODE
// finds the index of the smallest value from 'start' to the end
public static int minIndex(int[] arr, int start) {
    int minIndex = start;                    // assume the first item is smallest
    for (int i = start + 1; i < arr.length; i++) {
        if (arr[i] < arr[minIndex]) {        // found something smaller
            minIndex = i;
        }
    }
    return minIndex;
}

public static int[] selectionSort(int[] arr) {
    int[] sorted = arr.clone();              // don't change the original
    int n = sorted.length;
    for (int i = 0; i < n - 1; i++) {        // last item is auto-sorted
        int min = minIndex(sorted, i);       // smallest of the unsorted part
        int temp = sorted[i];                // swap it into position i
        sorted[i] = sorted[min];
        sorted[min] = temp;
    }
    return sorted;
}

TRACE: {64, 25, 12, 22, 11}
i=0 -> smallest is 11 (idx 4), swap with 64 -> {11, 25, 12, 22, 64}
i=1 -> smallest is 12 (idx 2), swap with 25 -> {11, 12, 25, 22, 64}
i=2 -> smallest is 22 (idx 3), swap with 25 -> {11, 12, 22, 25, 64}
i=3 -> smallest is 25 (itself), swap does nothing -> sorted
Comparisons: 4 + 3 + 2 + 1 = 10

BIG O
Read by index (array): O(1)  -> address = start + index, no walking
Read the nth item (linked list): O(n) -> must walk from the head
Insert/delete in a linked list: O(1) ONLY once I'm already at the spot
  (relinking pointers is O(1), but finding the spot is O(n)).
  Inserting at the front is O(1).
Insert/delete in the middle of an array: O(n) -> items must shift over
Selection sort: O(n^2). Each pass scans the rest of the list, and there
  are about n passes: (n-1) + (n-2) + ... + 1 = n(n-1)/2, which is
  about n^2/2. Big O drops the 1/2, so it's O(n^2).

WHAT I USED TO THINK
- I wrote "reading an array is O(n)". Wrong. It's O(1) for arrays.
  It's the linked list that is O(n) for reading.
- I wrote "linked list insert/delete is O(1)". Only true after I've
  found the position. Finding it costs O(n), which my Week 4 delete code
  had to do (track previous + current) before it could relink.

IN MY OWN WORDS
Recursion is a function calling itself until it reaches a base case.
The base case is what stops it. Without one, the calls never stop and
the stack overflows (StackOverflowError in Java).

The call stack has two operations: push and pop. Every CALL to the
function pushes a new frame onto the stack. Each frame has its own
copy of the variables, so one call's num can't be read or changed by
another call's num. When the base case returns, frames are popped one
by one, each finishing its work with the value that came back.

"Loops may achieve a performance gain for your program. Recursion may
achieve a performance gain for your programmer. Choose which is more
important in your situation!"
Meaning: recursion is often cleaner to write, loops can be cheaper to run.

CODE
public static int fact(int num) {
    if (num == 1) {            // base case: stops the calls
        return 1;
    }
    return num * fact(num - 1);   // recursive case: smaller problem
}

TRACE: fact(3)
push fact(3) -> needs fact(2)
push fact(2) -> needs fact(1)
push fact(1) -> base case, returns 1
pop  fact(1)
fact(2) = 2 * 1 = 2, pop
fact(3) = 3 * 2 = 6, pop

fact(0) -> Stack over flow error. this code will run forever until the satck overflow cause the base case will never hit  <- fill this in after tracing

CODE (fixed version)
public static int fact(int num) {
    if (num < 0) {
        throw new IllegalArgumentException("factorial undefined for negatives");
    }
    if (num == 0 || num == 1) {     // base cases: 0! = 1 and 1! = 1
        return 1;
    }
    return num * fact(num - 1);
}

EDGE CASE I FOUND
fact(0) never hits "num == 1" in my first version. num goes 0, -1, -2...
and the stack overflows. Fix: make 0 a base case too, and reject
negatives first. Lesson: a base case must cover EVERY input the
function can receive, not just the ones I was thinking about.

BIG O
Time: O(n) -> one call per step down to the base case.
Stack space: O(n) -> n frames sit on the stack at the same time.
The loop version uses O(1) extra space. Same answer, different cost.
