CODE (optional, only if it helps)
public static int binarySearch(int[] arr, int target){
    int start = 0;
    int end = arr.length -1;

    int foundIndex = -1;

    while(start<=end){
        int mid = (start+end)/2;
        if(arr[mid] == target){
            foundIndex = mid;
            break;
        }else if(target<arr[mid]){
            end = mid-1;
        }else{
            start = mid +1;
        }

    }
    return foundIndex;
}
WHY BINARY SEARCH IS O(log n):
Every step throws away half of the remaining list. So the question is:
"how many times can I cut n in half before only 1 item is left?"
That number is log n.

Example: 1,000,000 items
1,000,000 -> 500,000 -> 250,000 -> ... -> 1
That takes about 20 halvings, so at most about 20 steps.
Linear search could take up to 1,000,000 steps for the same list.

If the list doubles to 2,000,000, I only need ONE extra step,
because one more cut brings it back to the old size.
That is why log n grows so slowly.

DAY 2 | DATE: 28/10/2026 | CHAPTER 02: Selection Sort
(memory, arrays vs linked lists, selection sort)
==================================================

IN MY OWN WORDS
Computer memory is like a wall of drawers outside a theatre. When I
store something, the computer gives me a drawer (allocates) and takes it
back when I'm done (frees).

Array: all items sit in drawers right next to each other. 10 items
need 10 free drawers in a row.
Linked list: each item carries a pointer to the next item's address, so
the items can sit in any free drawers, even far apart.

Because an array is one block, the computer can calculate where any
item is (start address + index) and jump straight there. A linked list
has no such shortcut. To reach the 7th node I must walk through
nodes 1 to 6 first.

In practice arrays are used more. Jumping to any index is fast, they
need less space (a list stores a pointer with every item), and neighbouring
items load into the cache together, so scanning is faster in real life.
Linked lists are still good when items are inserted or deleted a lot.

EXAMPLE
Drawers outside a theatre (memory).
Facebook-style usernames: an array of 26 slots (A to Z), where each slot
holds a linked list of names starting with that letter. The array jumps
to the right slot, and the list handles growth in that slot.

CODE
// finds the index of the smallest value from 'start' to the end
public static int minIndex(int[] arr, int start) {
    int minIndex = start;                    // assume the first item is smallest
    for (int i = start + 1; i < arr.length; i++) {
        if (arr[i] < arr[minIndex]) {        // found something smaller
            minIndex = i;
        }
    }
    return minIndex;
}

public static int[] selectionSort(int[] arr) {
    int[] sorted = arr.clone();              // don't change the original
    int n = sorted.length;
    for (int i = 0; i < n - 1; i++) {        // last item is auto-sorted
        int min = minIndex(sorted, i);       // smallest of the unsorted part
        int temp = sorted[i];                // swap it into position i
        sorted[i] = sorted[min];
        sorted[min] = temp;
    }
    return sorted;
}

TRACE: {64, 25, 12, 22, 11}
i=0 -> smallest is 11 (idx 4), swap with 64 -> {11, 25, 12, 22, 64}
i=1 -> smallest is 12 (idx 2), swap with 25 -> {11, 12, 25, 22, 64}
i=2 -> smallest is 22 (idx 3), swap with 25 -> {11, 12, 22, 25, 64}
i=3 -> smallest is 25 (itself), swap does nothing -> sorted
Comparisons: 4 + 3 + 2 + 1 = 10

BIG O
Read by index (array): O(1)  -> address = start + index, no walking
Read the nth item (linked list): O(n) -> must walk from the head
Insert/delete in a linked list: O(1) ONLY once I'm already at the spot
  (relinking pointers is O(1), but finding the spot is O(n)).
  Inserting at the front is O(1).
Insert/delete in the middle of an array: O(n) -> items must shift over
Selection sort: O(n^2). Each pass scans the rest of the list, and there
  are about n passes: (n-1) + (n-2) + ... + 1 = n(n-1)/2, which is
  about n^2/2. Big O drops the 1/2, so it's O(n^2).

WHAT I USED TO THINK
- I wrote "reading an array is O(n)". Wrong. It's O(1) for arrays.
  It's the linked list that is O(n) for reading.
- I wrote "linked list insert/delete is O(1)". Only true after I've
  found the position. Finding it costs O(n), which my Week 4 delete code
  had to do (track previous + current) before it could relink.

IN MY OWN WORDS
Recursion is a function calling itself until it reaches a base case.
The base case is what stops it. Without one, the calls never stop and
the stack overflows (StackOverflowError in Java).

The call stack has two operations: push and pop. Every CALL to the
function pushes a new frame onto the stack. Each frame has its own
copy of the variables, so one call's num can't be read or changed by
another call's num. When the base case returns, frames are popped one
by one, each finishing its work with the value that came back.

"Loops may achieve a performance gain for your program. Recursion may
achieve a performance gain for your programmer. Choose which is more
important in your situation!"
Meaning: recursion is often cleaner to write, loops can be cheaper to run.

CODE
public static int fact(int num) {
    if (num == 1) {            // base case: stops the calls
        return 1;
    }
    return num * fact(num - 1);   // recursive case: smaller problem
}

TRACE: fact(3)
push fact(3) -> needs fact(2)
push fact(2) -> needs fact(1)
push fact(1) -> base case, returns 1
pop  fact(1)
fact(2) = 2 * 1 = 2, pop
fact(3) = 3 * 2 = 6, pop

EDGE CASE I FOUND
fact(0) -> Stack over flow error. this code will run forever until the satck overflow cause the base case will never hit  <- fill this in after tracing

CODE (fixed version)
public static int fact(int num) {
    if (num < 0) {
        throw new IllegalArgumentException("factorial undefined for negatives");
    }
    if (num == 0 || num == 1) {     // base cases: 0! = 1 and 1! = 1
        return 1;
    }
    return num * fact(num - 1);
}

EDGE CASE I FOUND
fact(0) never hits "num == 1" in my first version. num goes 0, -1, -2...
and the stack overflows. Fix: make 0 a base case too, and reject
negatives first. Lesson: a base case must cover EVERY input the
function can receive, not just the ones I was thinking about.

BIG O
Time: O(n) -> one call per step down to the base case.
Stack space: O(n) -> n frames sit on the stack at the same time.
The loop version uses O(1) extra space. Same answer, different cost.

IN MY OWN WORDS
Divide and conquer is not an algorithm, it's a mindset. When I'm stuck
on a problem, I ask: can I split it into smaller versions of the same
problem? To use it I need (1) a base case that is simple enough to
solve directly, and (2) a recursive case that shrinks the problem.

Quicksort uses it:
1. Pick an element as the pivot.
2. Partition: smaller elements go left, larger go right (in my version,
   elements equal to the pivot go left). After this the array is NOT
   sorted, but the pivot is in its final position.
3. Do the same on the left part and the right part.
Base case: an array with 0 or 1 elements is already sorted.

EXAMPLE
{5, 2, 8, 1, 9, 3}, pivot 5
left (<= 5): {2, 1, 3}   pivot: 5   right (> 5): {8, 9}
Then quicksort {2,1,3} and {8,9} the same way.

BIG O
Average: O(n log n)
  - about log n levels of splitting (the pivot lands near the middle)
  - each level partitions every element once -> n work per level
  - so n x log n
Worst: O(n^2)
  - the pivot is always the smallest or largest element, so one side
    gets everything and the problem only shrinks by 1 each time
  - n levels x n work per level
Same Big O does not mean same speed: Big O hides constants, so two
O(n log n) sorts can differ in real speed.

IN MY OWN WORDS
A hash table stores data as key-value pairs. It is a hash function
plus an array: the function turns a key (a string or any data) into a
number, and that number is the slot where the value lives. That is why
lookup is fast: no searching, I jump straight to the slot.

A hash function must be CONSISTENT: the same input always gives the
same output. If "apple" gives 3 once, it must give 3 every time,
otherwise I can't find my item again.
A good one also spreads different keys across different slots.

Average O(1) for search, insert and delete.
Used for: fast lookups, avoiding duplicates, caching.

CODE
Map<String, Integer> ages = new HashMap<>();
ages.put("Ravi", 24);
ages.put("Pooja", 23);
System.out.println(ages.get("Ravi"));    // 24

// duplicate check (voting)
Map<String, Boolean> voted = new HashMap<>();   // declared outside
public static void voteSystem(String name) {
    if (voted.containsKey(name)) System.out.println("Already voted!");
    else { voted.put(name, true); System.out.println("You can vote!"); }
}

(Prime sums ignore spaces and treat upper/lower case the same.)

COLLISIONS
A collision is when two DIFFERENT keys get the same slot. This is not
the same as inconsistency (one key giving different answers).
Fix: chaining. Each slot holds a linked list, so keys that land in the
same slot sit in the same list. This is the same idea as Chapter 2's
26-slot array of linked lists.
Collisions are why a hash function must spread keys evenly. If every
key lands in one slot, the table becomes one long linked list and
search drops from O(1) to O(n).
Also: when the table gets too full (high load factor = items / slots),
collisions pile up, so the table should resize to more slots.
The book's rule of thumb is to resize past a load factor of about 0.7

BIG O
Average: O(1) search, insert, delete (good hash function, low load).
Worst:   O(n) (everything collides into one slot).

WHAT I USED TO THINK
I mixed up a collision with an inconsistent hash function in 5.1.
A collision is two different keys sharing a slot. Inconsistency is the
same key giving different results. 5.1 was consistent but collided.

IN MY OWN WORDS
BFS answers two questions on a graph:
1. Is there a path from A to B?
2. What is the shortest path (FEWEST edges) from A to B?
If a problem asks for "shortest path to X", model it as a graph and
try BFS.

Graphs: DIRECTED has arrows (rama -> alex: rama owes alex money), and
the relationship goes one way. UNDIRECTED has no arrows and the
relationship goes both ways (ross dated rachel, rachel dated ross).

BFS uses a QUEUE (FIFO). It checks all 1st-degree connections before
2nd-degree ones, in the order they were added. That order is what
guarantees the shortest path. A stack (LIFO) would dive deep first.

Keep track of people already checked (a visited set). Otherwise I
re-do work, or loop forever when the graph has a cycle.
Trees don't need it because they never point back (my father can't
also be my great-grandfather).

EXAMPLE
Mango seller: check my friends, then friends of friends, then theirs.

CODE
public static Map<String, List<String>> createSocialNetworkGraph() {
        Map<String, List<String>> graph = new HashMap<>();

        graph.put("you", Arrays.asList("alice", "bob", "claire"));
        graph.put("bob", Arrays.asList("anuj", "peggy"));
        graph.put("alice", Arrays.asList("rekha"));
        graph.put("claire", Arrays.asList("thom", "jonny"));

        graph.put("anuj", new ArrayList<>());
        graph.put("peggy", new ArrayList<>());
        graph.put("rekha", new ArrayList<>());
        graph.put("thom", new ArrayList<>());
        graph.put("jonny", new ArrayList<>());

        return graph;

    }

    public static boolean findMangoSeller(Map<String, List<String>> friendsList) {
        Queue<String> searchQueue = new LinkedList<>();
        Set<String> searched = new HashSet<>();
        searchQueue.addAll(friendsList.get("you"));

        while (!searchQueue.isEmpty()) {
            String person = searchQueue.poll();
            if (!searched.contains(person)) {
                searched.add(person);
                if (isMangoSeller(person)) {
                    return true;
                } else {
                    searchQueue.addAll(friendsList.get(person));
                }
            }

        }
        return false;

    }

    public static boolean isMangoSeller(String name) {
        return name.endsWith("m");
    }

O(V + E): every person (vertex) is visited at most once, and every

WHAT I USED TO THINK
I thought having a "searched" set was enough. My first version only

Fix: add the person to the set as soon as I start processing them
(searched.add(person)), before looking at their friends.

Lesson: a visited set needs both halves. Check it, AND fill it. The
condition was right, but the action was missing. Same family of bug as
the missing return in my recursive binary search.
